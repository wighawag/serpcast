## The socks5h check (the task asked to verify and record it)

Measured 2026-09-28 with Chrome for Testing 151.0.7922.34 (Playwright's build), headless, against a local SOCKS5 server that records the CONNECT request's address type, and a local HTTP server mapped with `--host-resolver-rules` to catch a direct connection:

- `--proxy-server=socks5://…`: every request reached the proxy with ATYP 3 (a domain name, e.g. `DOMAIN:example.com`): **Chromium resolves host names at a SOCKS5 proxy.**
- `--proxy-server=socks5h://…`: **not accepted**; nothing reached the proxy and nothing went direct (the page simply did not load).
- `socks://…` behaved like `socks5://`.
- End to end through serpcast library mode and the real searchcast 0.1.1 with `proxy: 'socks5h://…'`: the target host reached the proxy as `DOMAIN:leaktest.example`.

So serpcast passes `socks5h://` to Chromium as `socks5://` (`chromiumProxy`, tested on the translated argument), and any other scheme as given. Consequence worth knowing: a caller's plain `socks5://` resolves locally in the HTTP transport (libcurl) but at the proxy in the browser. Not changed here (it is the more private direction). Not measured: a proxy URL with credentials (Chromium's `--proxy-server` has no place for them); serpcast passes it through as given.

## Decisions

1. **Engine shape: `{name, searchcast: {recipe}}` (library) or `{name, searchcast: {endpoint, recipe?, timeoutMs?}}` (endpoint)**, told apart from recipes by the `searchcast` object (`isBrowserEngine`), and the mode by `endpoint` being present. Type name `BrowserEngine` (CONTEXT's term). In library mode `recipe` is a `serpcast-recipe` Recipe object; in endpoint mode it is the recipe's name on the server. Alternative: two separate fields (`recipe` vs `recipeName`), or a factory function. Touches: webveil's engine configuration.
2. **Endpoint `recipe` defaults to the engine's `name`** (searchcast names recipes by their `name` field, so the two usually match). Alternative: required, or omitted from the query (searchcast then picks its only recipe, and fails with `input` when it has several).
3. **Endpoint `endpoint` is one string: an `http(s)://` URL, or a Unix socket path when it starts with `/`**, mirroring searchcast's own `--listen` convention. Any other scheme is a `recipe` error (the engine is misconfigured); a string that is not a URL at all ends up `transport` ("cannot reach"). A base path in the URL is kept (`/search` appended).
4. **Endpoint `timeoutMs` defaults to 30 s** (twice `DEFAULT_TIMEOUT_MS`), because searchcast spends up to the recipe's 15 s itself and a cold browser start comes on top. A missed deadline is `timeout`. User-visible default. Library mode has no serpcast-side deadline (searchcast bounds the page by the recipe's `timeoutMs`); the caller's `signal` still rejects at once.
5. **The endpoint request never goes through serpcast's proxy**: it is the caller's local service; serpcast cannot control that browser's egress (README says so). Alternative: send it through the proxy (would break a loopback or Unix-socket endpoint).
6. **Mapping beyond the task's table:** an unknown `error` code, an error status with a JSON body without `error`, a 200 without a results array, a result without `title`/`url`, and an unreachable endpoint are `transport`; a non-2xx is judged by `error` first. In library mode a thrown error without a `code` (not a `SearchcastError`) is `transport` too, not rethrown as a serpcast bug (chain decision 8 rethrows non-`SerpcastError`s): it comes from searchcast or the browser. Results are normalized with the declarative runner's rule (`snippet` from `content`/`snippet`/`description`; `normalizeResult`, now exported from `declarative.ts`); non-string fields are dropped.
7. **Library-mode setup failures are `transport`**: `searchcast` not installed ("npm install searchcast"), no browser found (no `chrome` and `findChrome()` finds none), Xvfb failing to start. Same kind as searchcast's own `browser` code (the browser could not be started). So a chain with a browser engine last and no searchcast falls through to `exhausted`. Alternative: `recipe` (misconfigured engine), or a thrown non-engine error (would abort chains that did not need the browser). Touches: CONTEXT's `transport` wording ("the network or the server failed") is stretched to "the browser could not be started".
8. **`searchcast` library options live on `createSerpcast({searchcast: {chrome, xvfb, headless, profile, concurrency, chromeArgs, module}})`**, names following searchcast's CLI flags, because one browser serves every library-mode engine of the instance and the proxy is the instance's. `module` injects a searchcast module (tests, forks), like the `transport` option. `chromeArgs` and `concurrency` were not asked for; they are searchcast's own knobs, passed through. Alternative: options per engine (one browser per engine).
9. **Lazy start and restart:** the searchcast module is imported, the profile created and Xvfb started on the first search that reaches a library-mode engine (never at `createSerpcast`, so the no-disk test still holds). A failed start is retried on the next search. After `close()`, a later search starts a fresh browser (and a fresh temporary profile). Browser engines have no serpcast session (the browser keeps cookies in its profile); cooldowns apply as for any engine.
10. **Temporary profile:** `mkdtemp` in `os.tmpdir()`, prefix `serpcast-profile-`, mode 0700 (mkdtemp's own mode, asserted in the test). Deleted on `close()` (after searchcast has stopped the browser and Xvfb) and by a synchronous `process.once('exit')` handler, removed on `close()`. searchcast prepends its own exit handler that kills the browser, so the browser is gone before the directory is removed. A process killed by an unhandled signal fires no `exit` (README says to call `close()` on shutdown).
11. **`searchcast` is an optional peer dependency `>=0.1.1`** (not `^0.1.1`, which for a 0.x would refuse 0.2, likely the release that adopts `serpcast-recipe`). serpcast types only the part it uses (`SearchcastModule`), so it never needs searchcast's types. It is imported with a variable specifier, only in `browser.ts` (a test asserts this). pnpm installs optional peers in this workspace (the lockfile gains `searchcast@0.1.1`), so the "not installed" test mocks the import failing (`test/browser-missing.test.ts`), and `test/browser.test.ts` checks the real package has the shape serpcast uses.
12. **`untilAborted` is now exported from `code.ts`** (not from the package) and reused for library-mode aborts.
