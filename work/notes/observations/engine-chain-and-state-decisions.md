# engine-chain-and-state: in-scope decisions

2026-09-28, task `engine-chain-and-state`. None of these meets the ADR bar on its own; recorded here so the reviewer and the later tasks (`code-recipes`, `searchcast-engine`) and webveil's `serpcast-backend` can ratify or reverse them. The code-level ones are also stated in the module comments of `packages/serpcast/src/serpcast.ts` and `src/store.ts`, and the user-visible ones in the README ("Engine chain (`createSerpcast`)", "State store").

## Decisions

1. **Store interface: `get(key)`, `set(key, value, {ttlMs?})`, `delete(key)`, values plain JSON (`JsonValue`), expiry relative (`ttlMs`), named `StateStore` (CONTEXT's "State store").** Relative TTL is what Redis/Keyv-style stores and a per-identity file store take naturally. Alternative: an absolute `expiresAt`. Touches: webveil's per-identity file store (it must implement this), `code-recipes` (`ctx.session` JSON state lives in the same session record).
2. **serpcast does not trust the store's expiry alone.** Each record carries its own time (`{until}` for a cooldown, `{cookies, lastUsed}` for a session), checked with serpcast's `now` clock; the TTL is passed so the store can garbage-collect. So a lazily-expiring or clock-skewed store stays correct, and the injectable clock drives the tests. Boundaries match the memory store: a session is alive while `now - lastUsed < sessionIdleMs`, an engine is skipped while `now < until`.
3. **Keys:** `engine/<encodeURIComponent(name)>/session`, `engine/<name>/cooldown`, plus one non-engine key `serpcast/sessions` (an index of engine names with a session, TTL refreshed with each session save). The index exists because the task's interface has no key listing, and `clearSessions()` with no argument must find sessions saved by an earlier process in a persistent store. Alternative: add `keys()`/prefix listing to the interface (heavier for implementers), or clear only engines this instance used (misses a persistent store's older sessions). Costs one extra `get`+`set` per engine run. Touches: any caller that inspects its store.
4. **Engines in cooldown are reported in `failures`** with a synthetic `blocked` error ("skipped, blocked earlier, cooling down until <ISO time>"), although the task says failures list engines "tried". Reason: otherwise a chain whose engines are all cooling down throws `exhausted` with an empty `failures`, which reads like "no engines"; and a caller sees why its preferred engine did not answer. A skipped engine's cooldown is not extended. Alternative: omit skipped engines, or add a `skipped: true` flag (a new concept). Touches: webveil's reporting of failures.
5. **Defaults: `cooldownMs` 5 minutes, `sessionIdleMs` 10 minutes** (exported as `DEFAULT_COOLDOWN_MS`, `DEFAULT_SESSION_IDLE_MS`). The task says "a few minutes" for the cooldown and gives no idle default; 10 minutes keeps a burst of searching on one session while "nothing outlives a burst". User-visible defaults, easy to change.
6. **Only `blocked` starts a cooldown.** `timeout`, `transport` and `recipe` are recorded and the next engine is tried, with no cooldown (a flaky network or a stale recipe is not the site refusing).
7. **Sessions are saved after every engine run, whatever the outcome** (success, failure, abort), so cookies set by a challenge or `blocked` page are kept for the next attempt. Concurrent searches on one engine race and the last save wins (no locking; the store interface has none). Alternative: save only on success.
8. **Errors that are not a `SerpcastError` are rethrown**, not recorded as engine failures: for declarative engines they can only be a bug in serpcast, and hiding them behind a fallback would mask it. An abort rejects with the signal's reason (transport decision 7) and is never a failure. `code-recipes` may want to wrap a code recipe's arbitrary throw as a `recipe` failure instead; that is its call.
9. **An empty `engines` list throws `exhausted`** with `failures: []` (message "no engines to search"), rather than a new usage error.
10. **`maxResults` only cuts the answer**; each recipe's own `limit` still applies first (the declarative runner is unchanged).
11. **`transport` option** on `createSerpcast` (a `Pick<Transport, 'session'>`): replaces the transport built from the transport options. Needed to test with fake engines, and `code-recipes` plans to assert through "the injected fake transport". Alternative: test-only module mocking.
12. **`now` option** (the injectable clock the task asks for), shared with the default memory store. Cookie expiry inside `CookieStore` still uses the real clock (unchanged).
13. **`clearSessions(engine?)` takes an engine name** (a string), matching how engines are identified (CONTEXT: "identified by its name"). **`close()` is a no-op for now**; `searchcast-engine` will stop its browser there. A search after `close()` is not refused.
14. **`SerpcastError` gained an optional `failures` field** (set only for `exhausted`), and the type `EngineFailure = {engine, error}` lives in `errors.ts`.
15. **`Engine` is, for now, an alias of `Recipe`.** `code-recipes` and `searchcast-engine` will widen it to a union; a code recipe is distinguishable by its `search` function.
