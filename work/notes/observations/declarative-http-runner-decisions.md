# declarative-http-runner: in-scope decisions

2026-09-28, task `declarative-http-runner`. None of these meets the ADR bar on its own; recorded here so the reviewer and the later tasks (`engine-chain-and-state`, `code-recipes`, searchcast's `use-serpcast-recipe`) can ratify or reverse them. The code-level ones are also stated in the module comments of `packages/serpcast/src/declarative.ts`, `src/html.ts` and `src/cli.ts`, and the user-visible ones in the README ("Declarative recipes over HTTP", "CLI: `serpcast query`").

## Decisions

1. **`ready` is checked before `empty`, as searchcast does, not in the task's listed order.** The task's "What to build" lists the decision order as blocked, then `empty`, then `ready`; searchcast@0.1.1's probe (`src/probe.ts`) checks `ready` first and only looks at `empty` when `ready` is absent. The two differ only on a page where both selectors match: searchcast returns the results (or, with no usable item, never answers `empty`), the listed order would return `[]` and drop real results. The task's Prompt says "match searchcast's semantics ... so a recipe behaves the same in both runners" and names exactly one deliberate difference (timeout vs `recipe`), so searchcast's order was kept. Tested (`checks ready before empty, as searchcast does`). Reversal is a two-line swap in `decide()`. Touches: searchcast parity; every recipe whose `empty` element can sit on a results page.
2. **`blocked` selectors are applied to non-2xx bodies too, before the status mapping.** Order in `decide()`: 202/403/429, `blockedUrl`, `blocked` selectors, then 404/410 (`recipe`) and other non-2xx (`transport`), then `ready`/`empty`. So a challenge page served with 503 (a common pattern) reads as `blocked`, which starts a cooldown in the engine chain, rather than as `transport`. Alternative: map non-2xx statuses before parsing. Touches: `engine-chain-and-state` cooldowns.
3. **Redirects:** 301/302/303/307/308 with a `Location` are followed by the runner, at most 20 (Chrome's limit), each hop a `document` request (typed-URL navigation, no referer) through the same session so cookies apply per hop. More than 20 is a `transport` error, as is an unparseable `Location`; a 3xx without `Location` falls under "other non-2xx" (`transport`). `blockedUrl` is matched against the final URL only (searchcast's `location.href` is the final URL too). Alternative: `recipe` for a redirect loop (rejected: it is the site's behaviour, not the recipe's).
4. **Public API:** `runDeclarativeRecipe(recipe, query, {session, signal?})` resolving `{recipe, results}`. `session` is `Pick<TransportSession, 'request'>`, so tests inject a fake and the engine chain passes each engine's transport session. Output omits searchcast's `query` and `elapsedMs` (the task asks for results plus the recipe name). Touches: `engine-chain-and-state` (wraps it into `{results, engine, failures}`), `code-recipes` (reuses `SearchResult`).
5. **Result shape is flat:** `{title, url, snippet?, ...extra}`, every other field passed through as a string (task: "extra fields pass through"), with `snippet` the first present of `content`, `snippet`, `description`. So a recipe with a `content` field yields both `content` and `snippet`. Alternative: nest extras under a `fields` key, or drop the field used for the snippet. Touches: `engine-chain-and-state`, `code-recipes` (its validation of the normalized shape should allow extra string fields).
6. **Timeout:** the recipe's `timeoutMs` (default `DEFAULT_TIMEOUT_MS`) bounds the whole call, redirects included, through the runner's own timer (so a transport that ignores its time limit still ends in `timeout`); each hop also gets the remaining budget as the transport's `timeoutMs`. The caller's abort rejects with the signal's reason (like the transport, its decision 7).
7. **Parser and selector engine:** htmlparser2 12 + css-select 7 (plus `domhandler` for types). Closure about 2.4 MB installed, about 320 KB of JavaScript. Chosen over node-html-parser (3.3 MB, bundles an older css-select and a non-standard parser) and parse5 + css-select (2.5 MB, needs an adapter). css-select runs with `relativeSelector: false` so a field selector has `querySelector` semantics (ancestors outside the item may match the left part). An invalid selector is a `recipe` error at once (searchcast would swallow the in-page exception and end in `timeout`).
8. **Visible text approximates `innerText`** without layout: `script`, `style`, `template`, `noscript`, `head` and `hidden` elements are dropped, block elements and `<br>` separate words, whitespace collapsed as searchcast does. CSS-hidden elements are not seen. The page is decoded with the `content-type` charset (the transport's `text()`), not `<meta charset>`. `href`/`src` are resolved only on the elements where the DOM property is a URL (`a`, `area`, `link`; `img`, `script`, `iframe`, ...), against `<base href>` or the final URL; on other elements the raw attribute is returned, as `getAttribute` would.
9. **CLI exit codes: 0 results, 1 a typed failure (`serpcast: <kind>: <message>` on stderr), 2 a usage error.** The scaffold's stub exited 1 on an unknown command; it now exits 2 like every usage error (its test was updated). An unreadable or invalid recipe file is reported as kind `recipe` (exit 1), since it is "the recipe does not fit the runner". JSON is printed with 2-space indentation, like `searchcast query`. Alternative: searchcast's single exit code 2 for everything. Touches: `libcurl-install-and-doctor` (its commands should follow the same exit-code convention).
10. **A hand-built `Recipe` without `navigate`** (bypassing `parseRecipe`) is rejected with the same `form` message rather than crashing; the runner does not re-validate recipes otherwise.
