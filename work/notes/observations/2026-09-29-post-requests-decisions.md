# Decisions made while building post-requests (2026-09-29)

Recorded for the `post-requests` done record. Code sites: `headerTable`, `preflightTable` and `isSafelistedContentType` in `packages/serpcast/src/chrome.ts`; `postBody`, `checkPreflight`, `PostOptions` and `MAX_REQUEST_BODY_BYTES` in `packages/serpcast/src/post.ts` (new); the preflight step and connections in `createTransport` (`packages/serpcast/src/transport.ts`); `http.post`/`http.postJson` in `packages/serpcast/src/code.ts`. Measurement: `work/notes/findings/post-requests.md`.

Reality check first: the task's premises held. The transport was GET only, POST was listed as not measured in `chrome.ts` and in the finding, and nixpkgs Chromium 152.0.7977.82 (the version of the earlier captures) was available. The capture found one thing the task did not anticipate: Chrome sends the preflight on a SEPARATE connection (decision 3).

1. **Preflights are sent, not refused.** The task allowed either. Refusing would have made every JSON POST to a sibling API host (`api.example.com` from `www.example.com`, the motivating kind of flow) impossible; sending it as captured keeps those flows coherent with a browser. Alternative: refuse with a `recipe` error; rejected as too limiting.
2. **The POST is modelled as `credentials: 'include'`**, as `fetch` GETs already are (decision 1 of `2026-09-29-sec-fetch-site-by-initiator-decisions.md`): the session's cookies are sent, and a cross-site POST carries `sec-fetch-storage-access: active`. The preflight itself is always credential-less (no cookie, no storage access), as measured.
3. **Preflights use their own connections.** Chrome keeps credential-less requests off the credentialed connection, so each transport session now has a second, credential-less set of connections (a second libcurl multi handle) used only for preflights; `session.close()` closes both. Never shared across sessions, like the first. Alternative: send the preflight on the session's normal connection (simpler, but a browser never does that when the POST is credentialed). Touches the `session-connection-reuse` model (a session may now hold two connections to one origin).
4. **The preflight is checked as Chrome checks it for a credentialed request**, and a refusal stops the POST (it is never sent): an ok status (2xx), `access-control-allow-origin` equal to the page origin (`*` refused), `access-control-allow-credentials: true`, and `content-type` in `access-control-allow-headers` (case-insensitive; `*` is not a wildcard for credentialed requests). The method is not checked (POST is CORS-safelisted). **New errors:** the preflight's status maps like the declarative runner's (202/403/429 `blocked`, 404/410 `recipe`, other non-2xx `transport`); CORS headers that do not allow the POST are `recipe` (the recipe's page/referer does not fit the site). This is the one place the transport interprets a status (it otherwise does not), because only it knows whether the POST may follow. The ACTUAL POST's response is not CORS-checked (the request is already sent; the recipe sees the raw response).
5. **Preflight cache, per transport session, in memory only:** keyed by page origin and URL, kept for `access-control-max-age` seconds (default 5, measured; capped at 7200 per Chromium's source, not measured; `0` is not kept, an unparsable value falls back to 5). Not in the state store (it is connection-level state, like the connections). Alternative: preflight every time; rejected because Chrome visibly does not.
6. **`method: 'POST'` only on the `fetch` kind**, as a new `RequestOptions` variant `PostOptions` (`{kind: 'fetch', method: 'POST', referer, fetchSite?, body?, contentType?}`); the GET variants gain an optional `method?: 'GET'`. Navigation (form) POSTs are out of scope (not measured). **New `recipe` errors (misuse only):** a POST on another kind, a method other than GET/POST, a body that is neither a string nor a `Uint8Array`, a `contentType` that is not printable ASCII (header injection), and a body over the cap.
7. **Body cap: `MAX_REQUEST_BODY_BYTES` = 1 MiB, fixed (exported, no option).** The task asked for a cap without a value; a proof-of-work answer or search form is a few KB. Not tied to `maxBodyBytes` (that bounds RESPONSES; re-meaning it would conflate two limits). Alternative: a `maxRequestBodyBytes` transport option; left out until someone needs it.
8. **`contentType` defaults like `fetch()`:** a string body without one gets `text/plain;charset=UTF-8`, bytes or no body get none (all measured). `postJson` sends `application/json` unless `options.contentType` says otherwise.
9. **An empty POST is sent as a bodiless transfer named POST** (`CURLOPT_CUSTOMREQUEST`), so its HEADERS frame ends the stream as Chrome's does; libcurl's own POST sent an empty DATA frame after the headers. Non-empty bodies use `CURLOPT_POST` + `CURLOPT_COPYPOSTFIELDS`, with libcurl's own `Content-Type` and `Expect` headers removed (the table's `content-length`/`content-type` are the only ones sent). Asserted on the wire.
10. **`ctx.http.get` forces `method: 'GET'`**, so a plain-JS recipe passing `method: 'POST'` to `get` still sends a GET, as before this task (GET behaviour unchanged). `ctx.http.post` requires `kind: 'fetch'` (else `recipe`, before any request), as the task's signature shows. `postJson` refuses a value `JSON.stringify` cannot serialize (`undefined`, a function) with a `recipe` error. New exported type `HttpPostOptions`.
11. **New exports:** `preflightTable`, `isSafelistedContentType`, `RequestMethod` (chrome.ts), `MAX_REQUEST_BODY_BYTES`, `PostOptions` (transport/post.ts), `HttpPostOptions` (code.ts). `headerTable`'s context gains `method`, `contentType`, `contentLength`; without them it is unchanged.
12. **Changeset: minor** (new request options, new `ctx.http` members, new exports).
13. **Size discipline:** the POST checks went into a new module `src/post.ts` rather than growing `transport.ts` further. The README's LOC table was already stale before this task (for example `transport.ts` listed at 280 while it had 496 lines); only the rows this task touches were updated, see `2026-09-29-loc-table-stale.md`.
