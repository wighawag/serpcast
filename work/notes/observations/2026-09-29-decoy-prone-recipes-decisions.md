# Decisions made while building decoy-prone-recipes (2026-09-29)

Recorded for the `decoy-prone-recipes` done record. Code sites: the `decoyGuard` bullet of the module comment in `packages/serpcast/src/serpcast.ts` (and its `decoyProne` helper), the header of `packages/serpcast-recipe/src/recipe.ts`.

Reality check: the task file sat in `work/tasks/backlog/`, not `ready/` as the dispatch said, and the spec in `work/specs/tasked/`. The premises held: `decoyGuard: string[]` in `createSerpcast`, `loadCodeRecipe` validating the default export, `parseRecipe` dropping unknown fields (so `decoyProne` had to be added explicitly to be kept).

1. **No caller-side off switch; OR semantics.** An engine is guarded when it is named in `decoyGuard` OR its recipe declares `decoyProne: true`. `decoyGuard` stays `string[]` only (no `{include, exclude}` form). To switch the guard off for a decoy-prone recipe the caller passes `{...recipe, decoyProne: false}`: engines are plain objects the caller already hands to `search`, so a per-call override exists without a new option (it works for a loaded code recipe too, since `search` is bound). Alternative: `decoyGuard: {include?, exclude?}`; rejected as a second shape for one option when the spread already does it. Reversible: adding the object form later is backward compatible. Touches the `decoyGuard` option (README table, JSDoc).
2. **`decoyProne: false` does not beat `decoyGuard`.** A recipe with `decoyProne: false` that the caller names in `decoyGuard` is guarded: the caller's explicit list is the stronger signal, and "false" is the same as absent. Alternative: false as an explicit opt-out that overrides the list; rejected, it would make the list silently ineffective.
3. **Browser engines:** a library-mode engine (`searchcast: {recipe}`) inherits its recipe's `decoyProne`. An endpoint-mode engine (`searchcast: {endpoint, recipe?: string}`) has only a recipe name, no recipe object, so it cannot inherit; the caller names it in `decoyGuard`. No `decoyProne` field was added to `BrowserEngine` itself (the task did not ask, and it would be a third place to declare it). Documented in the README decoy guard section.
4. **The schema addition is noted as the one deviation** from "exact extraction of searchcast's recipe.ts" in the `recipe.ts` header and the `serpcast-recipe` README intro, which previously said "unchanged". The new tests live in new files (`packages/serpcast-recipe/test/decoy-prone.test.ts`, `packages/serpcast/test/decoy-prone.test.ts`) so the searchcast-ported `recipe.test.ts` and the existing decoy tests are untouched. Error wording follows the existing styles: `recipe "<name>": decoyProne must be a boolean` (schema) and `code recipe <path>: "decoyProne" must be a boolean` (code recipes).
5. `loadCodeRecipe` omits `decoyProne` from its result when the module does not set it (like `timeoutMs`), and keeps `false` when set.
