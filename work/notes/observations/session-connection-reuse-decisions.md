# Decisions made while building session-connection-reuse (2026-09-29)

Recorded for the `session-connection-reuse` done record. The code sites are `Connections` and the module comment in `packages/serpcast/src/transport.ts`, and the "Connections" paragraph plus `acquire`/`release` in `packages/serpcast/src/serpcast.ts`. This supersedes decision 18 of `impersonated-transport-decisions.md` ("one connection per request").

Reality check first: the task's premises held (libcurl-impersonate 2.1.1, curl 8.21.0, Node 24.19.0, Linux x64). Every request was a fresh easy handle in its own multi handle, so every request opened a new TCP connection and TLS handshake. One premise needed a reading: the engine chain did NOT keep a transport session between searches (it made a new one per engine per search, from the store's cookies), so "the engine chain closes each engine's session connections when the session is dropped (idle expiry, `clearSessions`, `close()`)" only means something if the chain starts keeping them. It now does (decision 4).

1. **Connections are shared ONLY within one transport session, never across sessions.** Each session owns one multi handle (libcurl's connection cache, and in curl 8.x its TLS session cache too), created lazily on its first request. Two engines, or two callers, never share a connection or a TLS session ticket: that would link them at the TLS and IP layer. Alternatives: one multi handle per transport (per process), or a `CURLSH` share of the connection cache; both share across sessions and were rejected. Touches only the transport.
2. **A fresh easy handle per request, added to the session's multi handle** (not one easy handle per session reset between requests). `curl_easy_impersonate` and every option are applied to each new handle exactly as before, so the fingerprint setup is unchanged; the connection lives in the multi handle's cache, not the easy handle. `curl_easy_reset` would also wipe the impersonation settings, so a reused handle would have had to be re-impersonated anyway, with no gain. Asserted: the second request on a reused connection is stream 3 of the same connection, both HEADERS frames carry PRIORITY (exclusive, weight 256), and the second request's header table is exact.
3. **`CURLOPT_PIPEWAIT = 1` on every request (new).** Without it, concurrent requests of one session to one origin each opened their own connection (3 requests, 3 connections, measured); with it they wait for the first connection's ALPN and multiplex on it (1 connection), as Chrome keeps one HTTP/2 connection per origin. Cost: a concurrent request to an HTTP/1.1-only origin waits for the first connection to be set up before opening its own. Touches only the transport.
4. **The engine chain keeps each HTTP engine's transport session in memory between searches** (a map per `Serpcast` instance), so the next search reuses its connections. The state store stays the only source of cookies and state: the live session is reused only when the stored session is fresh AND the live session's cookies equal the stored ones (JSON compare); otherwise it is closed and a new one is made from the store, as before. So a second instance on a shared store that saved other cookies causes a new session (and new connections), never stale cookies. Alternative: always make a new session per search (as before) and close it after; that loses reuse across searches, which is most of the measured gain for a one-request engine.
5. **A search that starts while another search is running on the same engine gets its own transport session**, closed when it ends, instead of sharing the live one. This keeps the documented "two concurrent searches on the same engine each save their own cookies; the last save wins". Alternative: share the live session (one cookie jar for both, closer to one browser); rejected to keep the existing semantics.
6. **When the chain drops a session.** Idle expiry is checked at the next search with the chain's clock (a stale or missing store record drops the live session, even one with no cookies), AND an `unref`'d timer closes it after `sessionIdleMs` of real time without use, so an unused engine does not hold sockets open until the next search. `clearSessions(engine?)` and `close()` close them at once. A session dropped while a search is using it is closed again when that search ends (its last requests may have reopened a connection).
7. **`TransportSession.close()` is graceful and non-final** (new API). It closes the connections at once when idle, else when the requests in flight settle (they are not aborted), keeps the cookies, and a later request opens a new connection: no new refusal or error. Alternatives: abort in-flight requests on close, or refuse requests after close; both add a new error path for the chain's `clearSessions()` racing a search. Measured: `curl_multi_cleanup` of an idle session takes about 0.2 ms, also when the peer has stopped reading (no blocking shutdown on the main thread).
8. **`SerpcastOptions.transport` is now typed `ChainTransport`** (exported): a transport whose sessions MAY have `close()`. An injected transport written before `close()` existed keeps working (the chain calls `close?.()`); `createTransport()` sessions always have it. Touches the public `transport` option's type only (it accepts everything it accepted before).
9. **Idle connections never keep the process alive**: `Connections` schedules timers only while a request is in flight, so an idle session holds sockets inside libcurl but no Node handle. Tested with a child process that searches twice and must exit on its own, with and without `Serpcast.close()`. `process.exit()` tests pass unchanged; all libcurl calls stay on the main thread.
10. **One existing test changed**: `code-native.test.ts` asserted two CONNECT tunnels for a code recipe's two requests; with reuse it is one tunnel, which is this task's intended behaviour ("reuse through the same proxy connection"). The test server (`test/servers.ts`) now sets `TCP_NODELAY`, as real servers do: without it a response's second frame on a reused connection waited for the client's delayed ACK (about 40 ms), which made reuse look slower on localhost (46 ms vs 12 ms per request) in the measurement. It also gained `open` (connections still open) and `headersFrames()`.
11. **Changeset: minor.** New public API (`TransportSession.close()`, the `ChainTransport` type) and a behaviour change (connections kept open), so minor rather than patch.
12. **CONTEXT.md "Transport session"** now says it holds the session's open connections as well as its cookies (in memory only, never shared). No new term was introduced; "identity" was avoided in code comments, as the glossary asks.
