# Decisions made while building transport-no-deadlock-on-process-exit (2026-09-29)

Recorded for the `transport-no-deadlock-on-process-exit` done record. The first three are also documented at their code site in `packages/serpcast/src/transport.ts`.

Reality check first: both hangs reproduced as described (libcurl-impersonate 2.1.1, curl 8.21.0, Node 24.19.0, Linux x64), the in-flight one and the abort-then-exit one. With the fix both children exit in about 1.06 s (1 s delay plus Node start), and the new tests fail (hang, killed at 5 s) against the old code.

1. **The task's expected direction, as written: one multi handle per request, driven from main-thread timers.** Each request adds its easy handle to its own multi handle; `drive` calls `curl_multi_perform`, reads `curl_multi_info_read`, then `curl_multi_poll(…, 0)` (zero timeout, so non-blocking) to decide when to look again. It looks on the next event-loop turn (`setImmediate`) when a socket is ready or `curl_multi_timeout` says 0, otherwise after `curl_multi_timeout`, capped at `IDLE_POLL_MS`. A multi handle per request, not one shared per process, keeps "one easy handle (so one connection) per request, no connection reuse" exactly as before; a shared multi handle would share its connection cache across sessions, which is a separate decision. Alternative considered: `curl_multi_socket_action` with Node watching curl's sockets, which would need no polling but has no pure-JS way to watch a raw fd (it needs a native addon), so it was rejected.
2. **`IDLE_POLL_MS = 5`.** Measured with a server that accepts and never answers (plain HTTP, 3 s windows): 0 requests 0.01% of a core, 1 idle in-flight request about 0.6%, 10 about 1%. The cost is at most 5 ms of added latency to a network event that arrives while idle; while data flows the loop runs every turn (a 15 MiB local body takes about 20 ms). The test asserts under 25% of a core (a busy loop is about 100%).
3. **`CURLOPT_QUICK_EXIT = 1` on every handle (new).** An aborted or timed-out request is now cleaned up on the main thread. Without quick exit, libcurl's threaded resolver joins a pending DNS lookup on cleanup, which would block the event loop until `getaddrinfo` returns (before, that wait blocked a worker thread). The cost is a detached resolver thread that finishes on its own. Option id 322 confirmed at runtime with `curl_easy_option_by_name`. Touches nothing outside the transport.
4. **Abort no longer goes through `CURLOPT_XFERINFOFUNCTION`.** The progress callback is gone: the driver checks `signal.aborted` before each step and an abort listener schedules a step at once, which removes the handle and rejects with `signal.reason` (the same result as before, one event-loop turn after the abort instead of after libcurl's next progress call). If the signal aborts in the same step that libcurl completes, the abort now wins; before, the completed response won. `curl_easy_perform` (`Libcurl.perform`) and the `.async` type are removed from `libcurl.ts`, since nothing calls them.
5. **The `RTLD_NODELETE` pin stays, as the task asked.** Its JSDoc now says requests no longer run on worker threads and that the pin is kept without re-measuring exit without it (the library still starts resolver threads). ADR 0004's consequence line ("pinned to avoid a crash at process exit from BoringSSL thread-local destructors") is still accurate about why the pin exists and is left unchanged.
