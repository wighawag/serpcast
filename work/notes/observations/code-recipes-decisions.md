# code-recipes: in-scope decisions

2026-09-28, task `code-recipes`. None of these meets the ADR bar on its own; recorded here so the reviewer, `searchcast-engine` and webveil's `serpcast-backend` can ratify or reverse them. The code-level ones are also stated in the module comment of `packages/serpcast/src/code.ts`, and the user-visible ones in the README ("Code recipes").

Drift check at launch: the task still matched the code. The transport is GET-only (transport decision 5), so `ctx.http` exposes GET only, as the task's forward-note says; the engine chain's `transport` option (chain decision 11) is what the tests inject; `Engine` was an alias of `Recipe` (chain decision 15) and is now `Recipe | CodeRecipe`, told apart by a `search` function (`isCodeRecipe`). Like the earlier tasks, the body sat in `work/tasks/backlog/` and the spec in `work/specs/tasked/` although the runner prompt named `ready/` paths (see `task-launched-from-backlog.md`).

## Decisions

1. **`ctx.http` is `{get, text, json}`, each `(url, {kind, referer?, timeoutMs?})`.** `get` returns the raw `TransportResponse` whatever the status; `text`/`json` map statuses exactly as the declarative runner does (202/403/429 `blocked`, 404/410 `recipe`, other non-2xx `transport`) so a code recipe and a declarative one fail the same way on the same answer. No redirect following in any of them (a 3xx is `transport` for `text`/`json`; use `get` and follow by hand), because Chrome's header table for a redirected `fetch`/`script` hop is not measured. Alternatives: follow redirects in the helpers like the declarative runner; or return statuses without mapping. Touches: nothing outside code recipes.
2. **`kind` is required, with no default** (as in the transport's `RequestOptions`); a missing or unknown kind is a `recipe` error before any request. Alternative: default `document`, a new user-visible default. The context's `signal` is always attached to every request; the module cannot pass its own.
3. **Invalid JSON from `http.json` is a `recipe` error** (the response does not fit the recipe; often a challenge page served as HTML). Alternative: `transport`, or `blocked` (would start a cooldown on a mere API change).
4. **`ctx.session` is a synchronous key/value view: `get(key)`, `set(key, value)`, `delete(key)`**, values plain JSON, copied in and out; a non-JSON value (a `Date`, a class instance, `NaN`) is a `recipe` error. The state is kept in the engine's existing session record (`engine/<name>/session`, new optional field `state`), so it shares the cookies' idle expiry, `clearSessions()` and "saved after every run whatever the outcome" (chain decision 7), as chain decision 1 anticipated. Sync because it is loaded with the record before the run and saved with it after; no extra store round-trips. Alternatives: an async API writing through to the store per call (more store traffic, and a second key per engine), or a single JSON value instead of keys. Touches: any caller that inspects its store (the record gains `state` only when non-empty; declarative engines keep whatever state a record has).
5. **A code recipe may set `timeoutMs` in its export (default `DEFAULT_TIMEOUT_MS`, 15 s)**, bounding the whole search like a declarative recipe's `timeoutMs`; `ctx.signal` aborts then and the run is a `timeout` failure. The task named no time limit, but without one a hung module would hang the chain. Same name and meaning as the recipe schema's field. Alternative: no whole-search limit (only per-request transport timeouts).
6. **Any throw that is not a `SerpcastError` is wrapped as a `recipe` failure** (with the original as `cause`) inside `runCodeRecipe`, so the chain falls through to the next engine. This is the option chain decision 8 left to this task: for a code recipe an arbitrary throw is the module's fault, not a serpcast bug. A `SerpcastError` the module throws keeps its kind (so `impersonation` from `ctx.http` still aborts the whole search). An abort (caller or timeout) rejects with the signal's reason, whatever the module threw after it.
7. **`[]` from a code recipe is a valid answer** ("no results"), and the chain stops at it. CONTEXT says an empty list only comes from a recipe's `empty` selector; for a code recipe the module is its own `empty` selector, and it is told (README) to call `recipeError` when the response is not one it understands. Alternative: treat `[]` as a `recipe` error (would make a genuinely empty query impossible to answer). Touches: CONTEXT's `recipe` error / empty-list wording, which could be widened to name code recipes.
8. **Output validation:** an array of objects, every present field a string (fields set to `undefined` are dropped), non-empty `title` and `url`; anything else is a `recipe` error naming the result index. URLs are not parsed or resolved (the declarative runner resolves `href`; a code recipe builds its own). The chain's `maxResults` cut still applies after, and `ctx.maxResults` is only a hint.
9. **`loadCodeRecipe(path)` resolves a relative path against `process.cwd()`**, imports it with a `file:` URL, and returns a copy `{name, search (bound to the module object), timeoutMs?}`. A module that cannot be imported, or whose default export is not `{name: non-empty string, search: function, timeoutMs?: positive number}`, is a `recipe` error (as the CLI treats an unreadable recipe file). Node caches the import, so loading the same path twice returns the same module state. Also exported: `runCodeRecipe` (mirrors `runDeclarativeRecipe`) and `isCodeRecipe`.
10. **The abort race is not the declarative runner's `abortable()`**: `untilAborted()` in `code.ts` attaches its handlers to the module's promise before checking the signal, so a rejection after an abort is never unhandled (observation `declarative-abortable-unhandled-rejection.md`; tested with a module that rejects after its timeout).
11. **`serpcast query --recipe` still takes only declarative recipes.** Loading code from a CLI flag was not asked for. Candidate follow-up if recipe authors want it.
12. **Tests:** `test/code.test.ts` runs with the fake transport (extended to record `kind`, `referer` and a per-transport `proxy` label); `test/code-native.test.ts` runs a code recipe through the real transport, a local HTTP/2 server and a recording CONNECT proxy (skipped without `SERPCAST_LIBCURL_PATH`, like the other native tests; it passed locally against the pinned release). No real-site recipe is shipped or tested.
