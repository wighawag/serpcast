# Decisions made while building sec-fetch-site-by-initiator (2026-09-29)

Recorded for the `sec-fetch-site-by-initiator` done record. Code sites: `fetchSite`, `registrableDomain` and `headerTable` in `packages/serpcast/src/chrome.ts`, `RequestOptions` in `packages/serpcast/src/transport.ts`. Measurement: `work/notes/findings/sec-fetch-site-by-initiator.md`.

Reality check first: the task's premises held. `fetch` and `script` always sent `sec-fetch-site: same-origin` and the full `referer`; the nixpkgs Chromium available was 152.0.7977.82 (the same version the original tables were checked against). The capture showed the task's "and any header that changes with it" is more than the referer: see decisions 2 and 3.

1. **`fetch` is modelled as a credentialed request (`credentials: 'include'`).** Chrome's DEFAULT `fetch()` sends no cookie to another origin (even same-site) and then no `sec-fetch-storage-access`; with `credentials: 'include'` it sends cookies and, cross-site, `sec-fetch-storage-access: active`. serpcast's transport has always sent the session's matching cookies on every kind, so the tables follow the credentialed capture. Alternative: model the default `fetch()` (drop cookies for other origins); rejected because it would silently stop sending cookies a recipe may rely on (a change to the transport session's cookie semantics, not this task's). Touches the `fetch` kind only.
2. **A `fetch` that is not same-origin adds `origin: <page origin>`** (after `accept`), same-site included, as measured. `script` never does.
3. **A cross-site request adds `sec-fetch-storage-access: active`** (after `sec-fetch-dest`), for `script` and (per decision 1) `fetch`. Measured on Chromium 152 with third-party cookies allowed (the default); taken for the pinned Chrome 146 as the rest of the set is (the header shipped in Chrome 133).
4. **Registrable domain by a small built-in rule, no public suffix list** (no new dependency): an IP or single-label host is its own site; otherwise the last two labels, or three when the TLD has two letters and the label before it is one of `ac co com edu go gob gov ltd mil ne net or org plc sch`. Known limit, tested and documented (README, JSDoc): private suffixes (`github.io`, hosting platforms) and rarer public ones are not known, so `alice.github.io` to `bob.github.io` is `same-site` where Chrome says `cross-site`. Alternatives: vendor the PSL (about 250 KB, needs updating) or depend on a PSL package; rejected for size and the no-large-dependency ask.
5. **Sites are schemeful and ignore the port**, as measured: `http` to `https` on one host is `cross-site`; another port on one host is `same-site`. The task's wording ("same registrable domain = same-site") did not mention the scheme; the capture decided it.
6. **New request option `fetchSite?: 'same-origin' | 'same-site' | 'cross-site'`** on `RequestOptions` (so also on code recipes' `http.get/text/json`), allowed for `fetch` and `script` only (the type forbids it elsewhere). It overrides only the derivation: the dependent headers (referer, `origin`, storage access) follow the overridden value. Named after the header it sets; glossary entry "Fetch site" added to `CONTEXT.md`. `headerTable()` gains `url` and `fetchSite` in its context; without `url` it keeps the same-origin tables (so the existing tests and callers are unchanged). Exported: `fetchSite()`, `FETCH_SITES`, `FetchSite`.
7. **New `recipe` errors (misuse only):** a `fetchSite` on `document`, a non-`same-origin` `fetchSite` on `same-origin-navigation`, an unknown `fetchSite` value (a code recipe is plain JS), and a referer that is not an absolute URL when the request goes to another origin (it cannot be reduced to an origin). A relative referer to the SAME origin is not possible to detect without parsing either, so any unparsable referer with a `url` fails. Previously any referer string was sent verbatim; every caller in the repo already passes absolute URLs.
8. **`same-origin-navigation` stays same-origin and `document` stays `none`**, whatever the URL. Navigations to another origin were not measured (the task measured only `fetch` and `script`), and the kind's name says same-origin. Deriving for navigations would need a capture of link clicks and probably a new kind name; left for a later task.
9. **One line of an existing test changed:** `transport.test.ts`'s exact-table test for every kind used the referer `https://localhost/page` for requests to `https://localhost:<port>/…`, which is another port, so NOT same-origin (it is same-site). It now uses a referer on the server's own origin, which is what the test meant; its expectation is unchanged. The tests in `chrome.test.ts` (the literal same-origin tables) are unchanged.
10. **Changeset: minor.** New request option and exports, and a behaviour change for non-same-origin `fetch`/`script` requests.
11. **Not changed, captured as observations:** cookies ignore `SameSite` on cross-site requests (`2026-09-29-cross-site-cookies-ignore-samesite.md`; the stale comment in `cookies.ts` claiming every request is same-site was corrected), and `http://` targets get secure-context headers (`2026-09-29-http-targets-get-secure-context-headers.md`).
